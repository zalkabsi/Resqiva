## Current verified evidence

- `npm run lint`, `npm run typecheck`, `npm test` (163/163 in 19 files), and `npm run build` passed on November 4, 2026. `npm run smoke:local` and `npm run e2e:local` passed on November 3. Exact dates and scope are in [testing.md](testing.md).
- The real Resqiva preference-parser route returned validated preferences through the configured Fireworks service using only the required model. This is application-level AI evidence, not just a direct provider probe.
- The API smoke verified database-backed planning, a three-unit stock reservation and exact cancellation release, repeated requests, customer order history, and merchant dashboard data.
- Mocked route and transition tests cover store/pickup management, stock safety, bounded requests, customer and merchant reconciliation, capture/cancel races, and safe handling of uncertain PayPal states. The merchant E2E created a demo store and pickup window. These are not live payment or webhook evidence.
- The optimizer benchmark compared 12 deterministic seeded scenarios against the documented greedy baseline. Feasibility matched at 11/12 with zero independently checked optimizer output violations; it did not show a general performance advantage.
- PayPal order creation reached the Sandbox OAuth endpoint and was rejected with `invalid_client`. There is no buyer-approved order, capture, paid status, sold-stock update, or webhook delivery.
- `PAYPAL_WEBHOOK_ID` is missing. The webhook route returned HTTP 503 before processing an event.
- As observed November 4, the managed environment is connected/running with restricted network policy enforced. It allows `api.fireworks.ai` and `api-m.sandbox.paypal.com`; it does not allow `www.paypal.com` (browser JS SDK) or `www.sandbox.paypal.com` (buyer approval page). PayPal client bindings report ready, but the last actual OAuth test on November 3 returned `invalid_client`. `PAYPAL_WEBHOOK_ID` is absent from the current environment bindings.
